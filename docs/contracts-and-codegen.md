# Контракт і кодогенерація

Як живе межа API між хмарою, нодою і десктоп-UI: хто автор специфікації, які
зміни дозволені, і що робити, коли API треба змінити.

---

## 1. Хто автор специфікації

Специфікацію **не пише людина**. Її породжує huma з Go-типів у `mediary-cloud`:

```go
huma.Register(api, huma.Operation{
    OperationID: "getMedia",
    Method:      http.MethodGet,
    Path:        "/v1/media/{id}",
    Tags:        []string{"catalog"},
}, func(ctx context.Context, in *GetMediaInput) (*GetMediaOutput, error) { … })
```

Форма `GetMediaInput` / `GetMediaOutput` **і є** схемою в OpenAPI. Це головна
причина вибору huma: специфікація не може розійтися з кодом, бо вона з нього
виводиться, а не супроводжує його.

Спека — 3.1.0. `oapi-codegen` v2.8 і `openapi-typescript` 7.13 обидва її
читають; якщо колись знадобиться інструмент, який уміє лише 3.0, huma має
`OpenAPI.DowngradeYAML()` — тоді в `cmd/openapi` додається другий вихідний файл,
а не змінюється спосіб авторства.

## 2. Ланцюг

```
mediary-cloud                            приватний
  internal/modules/*/internal/handler   ← єдине місце, де оголошуються операції
  cmd/openapi                           ← `task openapi`
  api/openapi.yaml                      ← артефакт, комітиться

        │  scripts/sync-contracts.mjs (з кореня воркспейсу)
        ▼

mediary-contracts                        публічний
  openapi/cloud.openapi.yaml            ← точна копія, ніколи не редагується
  go/cloudclient/client.gen.go          ← oapi-codegen
  ts/src/cloud.gen.ts                   ← openapi-typescript

        │  тег go/vX.Y.Z + npm publish
        ▼

mediary-node/server     go get github.com/mediaryorg/mediary-contracts/go@vX.Y.Z
mediary-node/desktop    npm i @mediaryorg/mediary-contracts@X.Y.Z
```

Локальний API самої ноди цим шляхом **не йде**. Нода й десктоп-UI живуть в
одному репозиторії, тож `mediary-node/server/api/openapi.yaml` генерує TS-типи
прямо в `mediary-node/desktop/src/core/node/` — крос-репо хоп там був би
чистими накладними витратами. У contracts їде тільки межа хмара ↔ нода.

## 3. Правило сумісності

**Нода в полі старша за хмару.** Користувач може місяцями не оновлювати
десктоп-застосунок, а хмару деплоять хоч кілька разів на день ([TZ §3.1](../../TZ.md)).
Отже сумісність односпрямована: **свіжа хмара мусить обслуговувати стару ноду**.
Зворотне — стара хмара і свіжа нода — не гарантується й не тестується.

Для змін, які сумісно зробити **неможливо**, існує аварійний люк — версійний
гейт (§4). Він не заміняє правила нижче: вони працюють щодня, він — кілька разів
за життя продукту.

Звідси набір правил для змін у хмарному API:

| Зміна | Можна в minor | Чому |
|---|---|---|
| Новий ендпоінт | ✅ | стара нода про нього не знає й не викликає |
| Нове **опційне** поле у відповіді | ✅ | згенерований клієнт ігнорує невідомі поля |
| Нове **опційне** поле в запиті | ✅ | стара нода його не шле, сервер підставляє дефолт |
| Нове значення в enum | ⚠️ | лише якщо клієнт трактує невідоме значення як «інше», а не падає — це вимога до коду ноди, не до контракту |
| Нове **обов'язкове** поле в запиті | ❌ | стара нода його не шле → 422 на кожен виклик |
| Видалення/перейменування поля відповіді | ❌ | стара нода на нього розраховує |
| Звуження типу (`string` → enum, ширший → вужчий) | ❌ | те, що нода слала вчора, сьогодні невалідне |
| Зміна семантики поля без зміни імені | ❌❌ | найгірший варіант: нічого не ламається видимо, дані тихо псуються |
| Видалення ендпоінта | ❌ | лише через deprecation-вікно (нижче) |

**Deprecation-вікно.** Ендпоінт спершу позначається `Deprecated: true` в
`huma.Operation`, живе щонайменше **два релізи десктопа** (орієнтир — 6 місяців,
бо оновлення десктопа добровільне), і лише потім видаляється. Метрика
`mediary_http_requests_total` з міткою route показує, чи ним іще користуються —
видаляти наосліп не можна.

## 4. Версійний гейт — аварійний люк

Правила §3 — це механізм на кожен день. Але зміни, які **неможливо** зробити
сумісно, існують: дірка в безпеці, юридична вимога, міграція протоколу. Для них
хмара вміє оголосити мінімальну підтримувану версію клієнта.

Це люк, який відкривають кілька разів за життя продукту, а не заміна сумісності.
Розділ описує і механіку, і — важливіше — межі застосування.

### 4.1 Чому це не може бути дефолтом

Спокуса очевидна: «зробимо блокуючу модалку з проханням оновитись — і можна
ламати API вільно». Чотири причини, чому ні.

**Нода офлайн-first, і це не деталь, а її призначення.** Уся цінність ноди в
тому, що вона працює без хмари: користувач у літаку дивиться вже завантажену
серію з власного диска. Блокуюча модалка робить розклад деплоїв *віддаленого*
сервісу передумовою для перегляду файлу, який лежить у людини на диску. І
оновитися в той момент вона не може — мережі немає.

**Вікно між деплоєм і оновленням не нульове.** Вебзастосунок перезавантажив
вкладку і має новий код. Десктоп мусить завантажити інсталятор на сотні
мегабайт, можливо попросити права адміністратора, перезапуститися, на macOS
пройти Gatekeeper. Це хвилини — і воно регулярно не спрацьовує: немає місця на
диску, корпоративна політика забороняє інсталяції, антивірус зʼїв апдейтер,
протух сертифікат підпису. Якщо блок жорсткий, а шлях оновлення зламаний, у
користувача цеглина без виходу.

**Пастка з відкатом.** Хмара v2 форсить застосунок v2; у v2 знаходять критичний
баг; ти відкочуєш хмару на v1 — і тепер усі оновлені застосунки **новіші** за
хмару. Це рівно той напрямок, який §3 називає негарантованим. Форсований апдейт
не усуває несумісність, а переносить її туди, де вона бʼє під час інциденту.

**Швидкість деплою припиняється тихо.** Коли кожен деплой має видиму ціну для
користувача, команда починає їх уникати або перестає піднімати мінімальну
версію. За пів року сумісність підтримується все одно — просто неформально й без
правил у таблиці §3.

Для майбутнього мобільного клієнта все це гірше: додається ревʼю в сторі, тобто
дні латентності між «хмара вимагає нову версію» і «нова версія доступна».

### 4.2 Механіка

Хмара віддає вимоги на `GET /v1/health` — єдиному виклику, який кожен клієнт
робить на старті **без автентифікації**. Це навмисно: збірка, занадто стара щоб
її обслуговували, мусить мати змогу дізнатися чому.

```jsonc
{
  "status": "ok",
  "version": "1.4.0",
  "client": {
    "min_supported": "1.2.0",   // порожнє = гейт вимкнено
    "recommended": "1.4.0",     // порожнє = без підказки
    "update_url": "https://mediary.example/download"
  }
}
```

Налаштовується через `CLIENT_MIN_SUPPORTED_VERSION`, `CLIENT_RECOMMENDED_VERSION`
і `CLIENT_UPDATE_URL`. За замовчуванням **усі порожні** — гейт вимкнений, і це
нормальний стан деплою.

Дві перевірки на старті сервісу, обидві покриті тестами:

- `min_supported` не може бути новішим за `recommended` — «мусиш мати щонайменше
  2.0, і ми рекомендуємо 1.5» клієнту нема як показати;
- армований гейт **вимагає** `CLIENT_UPDATE_URL` — блок без виходу це цеглина,
  тож сервіс просто не стартує.

### 4.3 Як клієнт має це трактувати

Не бінарно й не на весь застосунок. Три рівні:

| Стан | Що показати | Що працює |
|---|---|---|
| `version >= recommended` | нічого | усе |
| `min_supported <= version < recommended` | ненавʼязливий банер «доступне оновлення» | усе |
| `version < min_supported` | банер «оновіться, щоб знову бачити свіжий каталог» | **усе локальне** |

Останній рядок — головний. Блокувати треба лише те, що справді залежить від
хмари: каталог, коментарі, синк прогресу. Бібліотека, плеєр, рідер і
завантаження мусять працювати — вони до хмари й не звертаються.

**Найелегантніше: деградувати в офлайн, а не в стіну.** Застосунок уже
зобовʼязаний коректно поводитися, коли хмара недосяжна — це окремий стан у
[плані десктопа](../../docs/plans/desktop-implementation-plan.md) §1.4.
Стан «хмара занадто нова для мене» функціонально **ідентичний** стану «хмари
немає»: каталог із кешу, локальне працює повністю, зверху банер із
`update_url`. Нового коду майже не треба — треба перевикористати наявну гілку.

Модальне вікно, що блокує весь застосунок, лишається на випадок, коли ціна
«користувач не може працювати» менша за ціну «користувач працює неправильно»:
інцидент безпеки, юридична вимога. Це рішення людини на момент інциденту, а не
поведінка за замовчуванням.

## 5. Версіонування

`go/` і `ts/` версіонуються **разом і однаково**: обидва описують одну спеку, і
розбіжність версій між ними означала б, що нода й UI бачать різний контракт.

- Go-модуль тегається `go/vX.Y.Z` (префікс обов'язковий — модуль лежить у
  підтеці `go/`).
- npm-пакет публікується як `@mediaryorg/mediary-contracts@X.Y.Z` — версія
  бампається один раз, у `ts/package.json`.
- `CLOUD_CONTRACT_VERSION` (`ts/src/version.gen.ts`) — та сама версія рядком,
  щоб нода й UI могли залогувати її на старті: у баг-репорті одразу видно,
  проти якого контракту зібраний клієнт. Файл **генерується** з
  `ts/package.json` за тим самим механізмом, що й `cloud.gen.ts` — див. §1.
  Це не друге місце для бампу версії, а похідне значення: зміни лише
  `ts/package.json`, `npm run generate` підхопить решту, а `npm run check`
  впаде, якщо хтось забуде перегенерувати.

Semver тут читається через призму §3: **major** — усе з колонки ❌;
**minor** — усе з ✅; **patch** — правки описів, прикладів, тегів.

## 6. Процедура крос-катної зміни API

Три PR, у цьому порядку. Спроба зробити їх паралельно закінчується тим, що CI
контрактів падає на дрейфі.

**1. `mediary-cloud`** — змінити handler, зареєструвати операцію.

```bash
task openapi          # оновлює api/openapi.yaml
task check
```

CI хмари має окремий гейт `openapi:check`: якщо `api/openapi.yaml` не
перегенеровано, збірка падає. Специфікація не може відстати від коду.

**2. `mediary-contracts`** — підтягнути спеку й перегенерувати.

```bash
# з кореня воркспейсу
node scripts/sync-contracts.mjs
```

Скрипт викликає `task openapi` у хмарі, копіює артефакт сюди й запускає
`npm run generate`. Далі — переглянути діф `go/cloudclient` і `ts/src`:
**діф генерованого коду — це і є ревʼю контракту**. Якщо в ньому зникло поле,
про яке ніхто не думав, це видно саме тут і більше ніде.

Потім теги й публікація.

**3. `mediary-node`** — підняти залежність:

```bash
cd server  && go get github.com/mediaryorg/mediary-contracts/go@vX.Y.Z
cd desktop && npm i @mediaryorg/mediary-contracts@X.Y.Z
```

## 7. Локальна розробка без публікації

Ганяти повний цикл релізу заради експерименту — марно. На час розробки:

- Go: `go.work` у корені воркспейсу або `replace` у `mediary-node/server/go.mod`
  на `../../mediary-contracts/go`;
- TS: `npm i ../../mediary-contracts/ts` (npm ставить її як `file:` залежність).

**Обидва обхідні шляхи мають зникнути до мержу.** `replace` у закомміченому
`go.mod` зламає збірку в будь-кого, крім вас; `file:`-залежність зламає
`npm ci` у CI. Це найпоширеніша помилка в цій схемі — CI ноди має окремо
перевіряти, що `go.mod` не містить `replace` на контракти.

## 8. Що перевіряє CI

| Репозиторій | Гейт |
|---|---|
| `mediary-cloud` | `api/openapi.yaml` збігається з кодом (`git diff --exit-code`) |
| `mediary-contracts` | `npm run check` — генерований вивід збігається зі спекою |
| `mediary-node` | збірка проти опублікованої версії контракту, без `replace` |

Жоден із цих гейтів не ловить порушення правил §3 — семантичну сумісність
машина не перевіряє. Це робота ревʼюера, і таблиця вище існує саме щоб ця
робота була механічною.
